# DLQ Replay

## 🎯 1. Описание Бизнес-Задачи
Падающая задача не должна крутиться бесконечно. После трёх ошибок она уходит в очередь мёртвых. Оттуда её можно вернуть в работу. Повтор не создаёт вторую задачу: это та же запись, которая после успешного прогона больше не числится мёртвой.

## ⚙️ 2. Обоснование Архитектурного Выбора
Статусы `queued`, `dead` и `done` лежат на самой задаче, а не в отдельном брокере. Так видно число попыток. Повтор сбрасывает признак отказа и ставит статус обратно в очередь, не копируя сообщение.

## 🗄️ 3. СУБД и Хранилища Данных
Задачи в SQLite. В бою то же место занимает очередь RabbitMQ и отдельная dead-letter очередь, правило «три попытки, потом ручной возврат» не меняется.

## 🔄 4. Интеграции и Сложный Стек
- Воркер вызывается явным тиком.
- Docker-порт `8122`. Проверка: `pytest test_main.py`.
- Контейнер: `docker compose up --build` из этой папки, порт `8122`.
- CI: `.github/workflows/medium-services.yml` на push запускает `pytest test_main.py` и `docker compose config`.
