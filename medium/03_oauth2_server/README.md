# OAuth2 Authorization Server

## 🎯 1. Описание Бизнес-Задачи
Магазину нужен свой сервер авторизации, а не вход через Google. Пользователь подтверждает доступ клиента, клиент меняет одноразовый код на access и refresh. Повторное использование уже повёрнутого refresh гасит всю цепочку токенов этой выдачи. Без scope `profile` почта не отдаётся.

## ⚙️ 2. Обоснование Архитектурного Выбора
Поток authorization code, а не password grant в API магазина: пароль видит только этот сервер. Секрет клиента и пароль лежат как PBKDF2, токены — как SHA-256, сырое значение возвращается один раз. Часы подменяемые, чтобы проверить истечение без `sleep`.

## 🗄️ 3. СУБД и Хранилища Данных
Пользователи, клиенты, коды и токены в SQLite. Код живёт 120 секунд и одноразовый, привязан к `redirect_uri`. В проде та же схема на PostgreSQL; Redis не обязателен, пока отзыв читается из таблицы токенов.

## 🔄 4. Интеграции и Сложный Стек
- `POST /oauth/token` принимает `authorization_code` и `refresh_token`.
- `POST /oauth/revoke` отзывает семейство токенов.
- Docker-порт `8103`. Проверка: `pytest test_main.py`.
- Контейнер: `docker compose up --build` из этой папки, порт `8103`.
- CI: `.github/workflows/medium-services.yml` на push запускает `pytest test_main.py` и `docker compose config`.
