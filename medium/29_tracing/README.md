# Tracing

## 🎯 1. Описание Бизнес-Задачи
Один заказ ходит в склад. Оба шага должны быть видны в одном трейсе: родительский span заказа и дочерний span резерва. Если на складе не хватает штук, ошибка ставится и на дочерний span, и на родительский. Успех оставляет оба span в `ok`.

## ⚙️ 2. Обоснование Архитектурного Выбора
Трейс собирается в процессе, без коллектора Jaeger: так видно связь parent/child без сети. Склад здесь функция с остатком в запросе, а не второй сервис. Правило то же, что у OpenTelemetry: ошибка ребёнка поднимается на родителя.

## 🗄️ 3. СУБД и Хранилища Данных
Spans лежат в памяти по `trace_id`. Для демо этого хватает. В бою те же поля уходят в коллектор, запрос их не хранит в заказе.

## 🔄 4. Интеграции и Сложный Стек
