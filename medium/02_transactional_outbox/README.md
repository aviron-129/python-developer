# Transactional Outbox

## 🎯 1. Описание Бизнес-Задачи
Счёт в биллинге не должен создаваться, если заказ не сохранился, и не должен создаваться дважды, если доставка события повторилась. Заказ и строка outbox пишутся в одной транзакции. Отдельный тик релея забирает неотправленные события. Биллинг принимает сообщение по `message_id` и повтор игнорирует.

## ⚙️ 2. Обоснование Архитектурного Выбора
Событие не публикуется внутри запроса создания заказа. Иначе падение брокера откатывало бы заказ или оставляло заказ без события. Релей идемпотентен: inbox помнит `message_id`, поэтому повторный тик не плодит счета.

## 🗄️ 3. СУБД и Хранилища Данных
SQLite с `BEGIN IMMEDIATE`. В бою та же схема ложится на PostgreSQL: заказ и outbox в одной транзакции, публикация — после коммита. Redis здесь не нужен, дедупликация лежит в inbox.

## 🔄 4. Интеграции и Сложный Стек
- `POST /relay/tick` — место воркера Celery или отдельного процесса.
- Прямой `POST /billing/consume` проверяет inbox без релея.
- Docker-порт `8102`. Проверка: `pytest test_main.py`.
- Контейнер: `docker compose up --build` из этой папки, порт `8102`.
- CI: `.github/workflows/medium-services.yml` на push запускает `pytest test_main.py` и `docker compose config`.
