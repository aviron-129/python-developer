# Multi-tenant Notes

## 🎯 1. Описание Бизнес-Задачи
Два арендатора живут в одном сервисе и не должны видеть чужие заметки. Запрос без арендатора отклоняется. Чужая заметка по прямому идентификатору выглядит как отсутствующая, а не как запрещённая: иначе по 403 можно перебирать чужие id.

## ⚙️ 2. Обоснование Архитектурного Выбора
Арендатор приходит заголовком и входит в каждый запрос к данным. Отдельной «глобальной» выборки нет. Это проще, чем схема на арендатора, и достаточно, чтобы изоляция была в условии SQL, а не в фильтре после чтения.

## 🗄️ 3. СУБД и Хранилища Данных
Заметки в одной таблице SQLite с колонкой `tenant`. В бою тот же предикат на PostgreSQL или отдельная схема на арендатора, если изоляция нужна жёстче.

## 🔄 4. Интеграции и Сложный Стек
- Заголовок `X-Tenant` обязателен.
- Docker-порт `8120`. Проверка: `pytest test_main.py`.
- Контейнер: `docker compose up --build` из этой папки, порт `8120`.
- CI: `.github/workflows/medium-services.yml` на push запускает `pytest test_main.py` и `docker compose config`.
