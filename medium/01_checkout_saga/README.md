# Checkout Saga

## 🎯 1. Описание Бизнес-Задачи
Оформление заказа не должно оставлять товар в резерве, если банк отклонил оплату. Сервис проводит один сценарий: списать остаток, провести платёж, подтвердить заказ. Если платёж отклонён, остаток возвращается, а заказ остаётся в состоянии `compensated` со списком шагов.

## ⚙️ 2. Обоснование Архитектурного Выбора
Оркестратор живёт в процессе, потому что шагов три и компенсации локальные. Отдельный workflow-движок здесь лишний. Платёжный шлюз скрыт за портом `SandboxPayments`: токен `decline` имитирует отказ банка без сети. Деньги хранятся целым числом в копейках.

## 🗄️ 3. СУБД и Хранилища Данных
Списание остатка и запись заказа идут в одной транзакции SQLite (`BEGIN IMMEDIATE` и `UPDATE ... WHERE on_hand >= ?`). Это тот же приём, что на PostgreSQL. Файл базы нужен только при `DATABASE_PATH`; тесты работают в памяти.

## 🔄 4. Интеграции и Сложный Стек
- Порт платежа можно заменить на Stripe или ЮKassa, не трогая оркестратор.
- Docker: `docker build -t checkout-saga .` и порт `8101`.
- Проверка: `pytest test_main.py` из этой папки.
- Контейнер: `docker compose up --build` из этой папки, порт `8101`.
- CI: `.github/workflows/medium-services.yml` на push запускает `pytest test_main.py` и `docker compose config`.
