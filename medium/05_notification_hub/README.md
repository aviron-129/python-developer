# Notification Hub

## 🎯 1. Описание Бизнес-Задачи
Одно событие заказа нужно разложить по каналам, которыми человек реально пользуется. Хаб рендерит шаблон и для каждого канала пишет доставку: отправлено или пропущено, потому что канал выключен. Если выключены все каналы, уведомление сохраняется как `suppressed`, а адаптеры не вызываются.

## ⚙️ 2. Обоснование Архитектурного Выбора
Каналы — это порт `RecordingBus`, а не прямые вызовы SMTP и Telegram. Предпочтения решаются до отправки, чтобы выключенный Telegram не получал сообщение «на всякий случай». Недостающий плейсхолдер в шаблоне отклоняет запрос целиком, без половины отправленных писем.

## 🗄️ 3. СУБД и Хранилища Данных
Получатели, шаблоны и доставки в SQLite. Журнал доставок нужен, чтобы показать, почему канал молчит. В бою адаптеры SMTP, push и Bot API подставляются вместо записывающей шины, схема та же.

## 🔄 4. Интеграции и Сложный Стек
- Каналы: email, push, telegram.
- Тело шаблона — `str.format` с полями из payload.
- Docker-порт `8105`. Проверка: `pytest test_main.py`.
- Контейнер: `docker compose up --build` из этой папки, порт `8105`.
- CI: `.github/workflows/medium-services.yml` на push запускает `pytest test_main.py` и `docker compose config`.
